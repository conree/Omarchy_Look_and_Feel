Apply and rollback contract

Transaction rules for changing Omarchy Look & Feel settings across application adapters.

StatusDesign contract; no configuration-writing adapter is enabledDate2026-10-21Settings contractsettings.schema.json, version 1

Purpose and limits

An Apply operation changes several independent application settings as one recoverable user action. It must either leave the selected values in place and verify them, or restore the recorded pre-Apply state and clearly report any incomplete recovery.

Scope: the controller may write only explicitly registered user-level targets under the user's home directory or through a documented per-user desktop API. It must not use sudo, edit package-owned files, run arbitrary shell commands from settings, or claim reversibility for a target it cannot restore.

Transaction sequence

  1. Validate. Validate the draft against settings.schema.json, confirm every selected ID exists in the current catalog, and check adapter preconditions. Automatic theme mode requires both theme IDs and a configured latitude, longitude, and IANA time zone.
  2. Acquire the transaction lock. Allow one apply or rollback at a time. Before starting a new Apply, restore every interrupted transaction under this lock. If recovery fails, stop and preserve its journal and snapshots.
  3. Snapshot exact targets. Record every file or supported API value an adapter may change before making any change. For regular user-owned files, preserve bytes, POSIX mode bits, and whether the file existed. Reject symlinks and paths outside the registered target list. Store snapshots in a private transaction directory with mode 0700; files use mode 0600.
  4. Write a durable journal. Record transaction ID, previous canonical settings, proposed settings, target list, snapshot hashes, and phase. Flush the journal before the first target mutation.
  5. Apply in a fixed order. Before each adapter runs, mark its target as in progress and flush the journal. Adapters must be idempotent, bounded to their declared targets, and expose a readback check.
  6. Verify readback. Read every changed target and verify the intended state. A successful process exit alone is not proof of application.
  7. Commit canonical settings. Write the new settings file through a temporary file in the same directory, flush it, then atomically rename it into place. Mark the journal committed only after the settings file and all adapter readbacks agree.

Atomic file writes

For each registered file target, write the complete new contents to a uniquely named temporary file beside the target. Flush the temporary file, apply the expected mode, and atomically replace the target. Flush the containing directory where the platform supports it. Never truncate a live configuration file in place. If a target needs a multi-file update, its adapter must enumerate all files in the transaction snapshot before changing the first one.

The first implementation supports regular files owned by the current user and restores their contents and POSIX mode bits. It does not capture ACLs, extended attributes, or ownership changes. Adapters must not manage files that depend on those metadata being preserved. Before each write, it compares the target with the saved snapshot; if another process changed the target, it preserves that change and marks recovery required rather than overwriting it during rollback.

Failure and interruption recovery

ConditionRequired behavior
Validation or precondition failureMake no changes. Show the failed check and keep the draft available for correction.
Adapter write or verification failureStop applying new targets. Restore changed targets in reverse order from the pre-Apply snapshots, then restore the previous canonical settings. Verify each restoration and report any target that could not be restored.
Process or machine interruption before commitOn controller startup, detect the prepared/in-progress journal and roll back from its snapshots before accepting another Apply.
Rollback failureKeep the journal and snapshots intact, mark recovery required, show the affected targets, and block further Apply operations until recovery is completed.
Target is not fully reversibleDo not include it in Apply. Treat it as an implementation blocker; do not downgrade it to a silent exception.

User rollback and backup retention

  • Provide a Revert action that restores the complete pre-Apply state for the most recent committed transaction, including the previous canonical settings.
  • Retain snapshots for committed transactions for at least 30 days and keep the 20 most recent transactions, whichever retains more. Never prune an in-progress or recovery-required transaction.
  • Before pruning, verify the transaction is committed and the snapshot hashes match its journal. Keep metadata and hashes with the retained snapshot.
  • Back up only the exact files an adapter manages. Do not copy whole browser profiles or unrelated application directories, which may contain credentials and private data.

Application restarts and session APIs

If an application reads configuration only at startup, the adapter must report “restart required” after readback confirms the saved file. The controller must not force-close user applications. For session APIs such as theme or icon settings, the adapter must capture the prior value and provide a compensating restore operation; if the API cannot report and restore its prior value, it is not transaction-safe.

Acceptance gates before the first writer

  1. Each adapter declares its exact target paths or API keys, required preconditions, readback method, and restoration method.
  2. The controller can recover an interrupted transaction before starting new work.
  3. Apply failure and rollback failure are visible and leave durable recovery information.
  4. The settings file is never committed while any adapter target is unverified.
  5. No adapter writes outside its allowlist or into package-owned Omarchy files.

Current implementation state: the transaction core is in transaction.py. Before a new Apply, it recovers interrupted transactions under the transaction lock and records recovered transaction IDs in the new journal. The controller also exposes explicit status, recovery, and rollback commands. Its application target allowlist is empty, so no application configuration can be written yet. A user-facing rollback control still needs integration before the Apply UI is exposed. No adapter is enabled.
